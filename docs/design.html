01Goals

CHANGED IN v0.7 — the memory budget was written against a machine that does not exist: the Pi has 463MB usable, not 512MB, and it is shared permanently with Pi-hole · every figure in §2.1 and §3.1 is re-derived from real measurements on the reflashed 64-bit board · the nightly resize moves into its own unit so its spike cannot take the display down

A Skylight-style family display for the kitchen wall. Web app — no APK — on an Android tablet (2019-era), served from a Raspberry Pi Zero 2 W on the home LAN, reading photos from a NAS on the same LAN.

  • The household's week at a kitchen glance.
  • Nothing visible until someone enters a PIN. The kitchen has visitors in it.
  • Groceries readable and writable by all three people, inside their session.
  • A one-tap guest mode showing an attractive screensaver and no household data.
  • Alex, Dana and Sam, with a visibility matrix Alex configures.

Not in v1

Writing to calendars. Events are read-only; no creating or editing from the wall. Also out: a month view, avatar photographs, anything on the NAS beyond file storage, and public internet access — this is a LAN appliance.

02Constraints

C1

463MB, shared with Pi-hole

A Zero 2 W that also serves the household's DNS. Rules out Docker, building on the device, and any on-demand image processing.

C2

A slow 2019 tablet

the tablet: Snapdragon 429, 2GB, 1280×800. Current Chrome, but a tight frontend budget.

C3

The NAS is a file server

The WD EX2 has locked firmware and no supportable container story. It stores files and nothing else.

C4

AnyList has no official API

A reverse-engineered library — and on the write path, which raises the stakes.

C5

Google expires tokens in 7 days

Any OAuth app in "Testing" status re-prompts weekly. Unacceptable on a wall display.

C6

The kitchen is semi-public

Visitors stand in front of this screen. Privacy is a requirement, not a preference.

2.1The Pi has 463MB usable, and Hearth is not its only tenant

A 1GHz quad Cortex-A53, wifi only, booting from an SD card. The board is sold as 512MB, but that is not what the OS gets, and Hearth does not get what is left. Measured on the actual device:

                                              MiB
  nominal                                     512
  VideoCore firmware + kernel reserve         -49   → 463 total
  Pi-hole + base system (measured, 64-bit)   -186   → ~277 for Hearth

The 512MB was never real. The VideoCore is the boot processor, not an optional peripheral — its firmware brings up the ARM cores and stays resident handling clock and power management, so it cannot be given zero. The floor is gpu_mem=16, which selects a cut-down firmware with no codecs, no 3D and a 1080p@16bpp early framebuffer — all correct for a headless board. The default of 64 costs 48MB for nothing.

The Pi also runs Pi-hole, permanently and by choice. It serves DNS for the whole household, which makes it more important than the wall display: a Hearth bug that exhausts memory must not take the family's internet with it. Hence hard MemoryMax= caps on every Hearth unit — a cgroup ceiling turns "Hearth leaked" into "Hearth restarted" rather than "the house is offline".

zram swap is mandatory — Raspberry Pi OS ships it enabled by default now (/dev/zram0, zstd, sized to the full 463MB of RAM), so nothing needs installing. The caps that follow are MemoryMax=224M with a 128MB heap for the server, and a separate MemoryMax=192M with a 64MB heap for the nightly resize, measured against a real Pi-hole install at ~186MB with database.maxDBdays=30 capping its query log.

2.2The NAS is a file server, not an app host

The NAS is a Marvell ARM appliance with locked firmware. Docker on My Cloud OS 5 exists only as a community modification that voids the warranty and is wiped by firmware updates. Nothing custom gets installed on it.

2.3Photos live on the NAS — and that is a relief

v0.1 planned to pull from Google Drive, because Google removed the photoslibrary.readonly scope on 31 March 2025 — the change that killed third-party photo frames and rclone's Google Photos backend alike.

None of that applies any more. Photos are already on the NAS, so the app walks a directory. The library is all JPEG, so sharp's prebuilt binaries handle it natively. This note survives only so that nobody later "improves" it by reconnecting Google Photos.

Still to measure: the CSS viewport

1280×800 is the panel, not the viewport. Android reports CSS pixels at the device's density, and an 8" 1280×800 screen sits close to a bucket boundary — at DPR 1.0 the landscape viewport is 1280px wide, at 1.5 it is nearer 853px, which falls outside the fluid range below. Read window.innerWidth on the device before layout work starts in phase 2.

The budget is tighter than the A7 Lite estimate in v0.3, not looser — the Snapdragon 429 is slower than a Helio P22, and there is only 2GB of RAM:

JAVASCRIPTUnder ~120KB gzipped. Server-render; hydrate as little as possible.
GPUNo backdrop-filter, no CSS blur(), no large box-shadow on scrolling content.
DOMWeek view only. A month grid is the likeliest place this device falls over, and a week is the right span for a kitchen anyway.
MEMORY2GB makes the nightly reload load-bearing rather than hygiene.
LAYOUTFluid across 1024–1340px rather than pixel-targeting one panel, until the real CSS viewport is measured.

2.5AnyList is unofficial — and on the write path

kevdliu/anylist is reverse-engineered, needs an AnyList email and password, and can break at any time. It remains the better of the two options, with real-time lists-update events and quantity support that upstream lacks. Because groceries are writable, a break means someone in the kitchen cannot add milk — mitigated by the write queue in §7.1.

The household list is "My Grocery List". AnyList accounts can hold several; the adapter resolves that name to a list id once at sync and stores it as the external_id of a sources row, so nothing downstream matches on a display name that someone could rename from their phone.

2.6OAuth tokens expire in Testing mode

Refresh tokens for an app in "Testing" publishing status expire after seven days. Set the consent screen to "In Production". Only one grant is needed — alex@example.com already has everything shared into it. Todoist uses a personal API token rather than OAuth, since there is exactly one Todoist user.

03Architecture

The tablet holds no credentials and talks to nothing but the Pi. It receives state over SSE and renders. The only things it sends back are PIN attempts, view changes, and grocery mutations.

3.1Storage layout

The NAS is mounted at /mnt/nas on the Pi.

/mnt/nas/hearth/
    pictures/       originals — the app NEVER writes here
    cache/          derivatives, nightly — 1280×800 landscape, 640×800 portrait
    backups/        nightly SQLite snapshots, 14 kept

/var/lib/hearth/                 ← on the Pi's SD card
    hearth.db       the live database
    fallback/       ~30 recent derivatives for when the NAS is away

The mount is read-write so cache/ and backups/ can be written. The read-only guarantee for originals becomes an application rule instead: nothing under pictures/ is ever opened for writing.

The live database must not live on the NAS

SQLite's locking depends on POSIX file locks that CIFS and NFS do not implement faithfully. Running a live database over a network mount is a well-known route to a corrupted file — and this one holds the PIN hashes and every provider's sync tokens.

hearth.db stays on the Pi's SD card and is copied to the NAS nightly with VACUUM INTO, which produces a consistent snapshot without stopping the app. That still gives the durability that motivated putting it on the NAS: the SD card can die and the most that is lost is a day of sync tokens, which simply re-sync.

3.2No public ingress

Webhooks would need a public HTTPS endpoint and therefore cloudflared on a 463MB device already sharing its memory with Pi-hole. Both providers support cheap delta polling instead — Google Calendar and Todoist every five minutes via sync tokens, AnyList by push, Open-Meteo every thirty. This removes the need for any inbound connection at all.

3.3Networking and deployment

  • Tablet → Pi: plain HTTP over LAN, http://hearth.local:8080. No TLS required — see §9.
  • Admin and OAuth → Pi: Tailscale Serve, giving real HTTPS on a *.ts.net hostname with no inbound firewall rules, for ~30MB of RAM.
  • Pi → NAS: CIFS mount at /mnt/nas, credentials in /etc/hearth/smb.cred mode 0600.

Never build on the Pi. Build on the Mac, rsync the output, restart the unit. The systemd unit sets Restart=always, MemoryMax=224M and a 128MB Node heap cap — sized in §2.1, not guessed. 64-bit Raspberry Pi OS is required, and the reason is better-sqlite3, not Node: Node 22 does ship linux-armv7l, but better-sqlite3 v13 bundles prebuilds for eight targets and 32-bit ARM is not one, with "gypfile": false so npm compiles no fallback. Only SQLite and the application live on the SD card, with journal_mode=WAL, batched transactions, and journald set to Storage=volatile.

4.1Two deliberate exclusions

The Todoist calendar is a duplication trap — Todoist's calendar-sync writes tasks into a Google calendar, so rendering both it and the Todoist panel would show every task twice. Weather for Springfield is an ICS feed redundant with Open-Meteo. The four football feeds collapse into one "Football" row rather than competing for space on an 8" panel.

4.2Timezone normalisation

The account's calendars disagree about timezones: Family is UTC, Culture calendar is America/Los_Angeles, Dana's is America/New_York, Visitors is Asia/Jerusalem. Left alone, all-day events land on the wrong day.

  • Household timezone is America/Toronto. Open-Meteo is queried at 45.5, -75.5.
  • Timed events store a UTC epoch and render in the household timezone.
  • All-day events store a YYYY-MM-DD local date string, never an epoch. Treating an all-day event as midnight-UTC is the classic off-by-one-day bug.

05Access model

The kitchen is a semi-public room, so no household data is visible without a PIN — including the grocery list. v0.3 proposed a PIN-free groceries button; that is dropped at Alex's decision, which leaves the model with a single gate and nothing to reason around.

  • Resting state is the family screensaver — photos, clock, date, weather. No events, no names.
  • Tap wakes the lock screen: three name chips and a Guest button. Names rather than photographs for now — unambiguous across three people, and one less asset pipeline in v1.
  • Name → PIN → session, showing that person's visible calendars and the grocery list.
  • Guest mode is sticky. It swaps to Unsplash and stays until someone enters a PIN, so family photos are not on display while visitors are over.
  • Idle for two minutes ends the session and returns to the screensaver. Five wrong PINs triggers a 60-second lockout.
Threat model, stated honestly

This stops dinner guests and visiting relatives from reading the family's schedule off the kitchen wall. It does not stop a determined attacker with physical access, and a PIN typed in a kitchen is observable. That is the right level of protection for the actual risk. PINs are argon2id-hashed regardless, because they will be reused from somewhere else.

6.1Standard

The week, and only the week — there is no month grid, for the performance reason in §2.4 and because a week is the right span for a kitchen. Calendars filtered by the visibility table, chips tinted by Google's own calendar colours. A bottom strip carries the next event, the grocery count, and — for Alex only — Todoist.

6.2Simple

A week grid is a scheduling tool for someone managing commitments. Sam is a young child; they want to know what they have to do and when. Top to bottom:

  1. Date header. The day name set large, the date beneath. No week number, no grid.
  2. Next up. The single next event, taking roughly a third of the screen: title, time, and a relative phrase — "in 2 hours", "at 16:30", "now" — with a colour bar from the owning calendar. This is the one thing they came to the tablet for.
  3. Rest of today. Up to four more rows of time · title · colour dot, at least 64px tall.
  4. Tomorrow. One compressed muted line, so they know to pack a bag tonight.
  5. Groceries. Full-width button. They can add to the list like anyone else.

Empty state is plain: "Nothing scheduled today." Type runs about 1.6× the standard view and touch targets are at least 56px. Their sources are their own calendar, Family, Joint, Visitors, Holidays and Culture calendar — no "Other people", no football.

6.3The interface follows the sun

A bright white 8" panel is a nightlight in a kitchen people walk through at night, and a dark one is hard to read in a sunlit room at noon. So the theme is not a fixed choice — it tracks sunrise and sunset.

  • Computed locally with suncalc from the pinned coordinates. No network call — the theme must not depend on Open-Meteo being reachable, and an astronomical calculation is deterministic and works offline.
  • The server owns the decision. It emits theme in the SSE state and sets a timer for the next transition. The client stays dumb, and the behaviour is testable by feeding the calculation a date.
  • Crossfade over about two seconds. An instant flip in a dark kitchen is unpleasant.
  • theme_mode is a setting — auto | light | dark, default auto.
  • After sunset the screensaver dims photos to roughly 80% brightness, which helps burn-in and stops the display dominating a dark room.

Springfield makes this more than cosmetic, because the winter case is extreme:

On 21 December the sun sets at 16:21, so the display is dark-themed through the whole of dinner and the evening. On 21 June it stays light until nearly bedtime. Both are right — the point is that the panel matches the room it is in.

07Photos and the write path

CHANGED IN v0.6 — two derivative shapes, and a slide that may hold two photos

Photos live at /mnt/nas/hearth/pictures/. The app walks that tree and never writes to it. Nightly at 03:00, single-threaded, with sharp.concurrency(1) and sharp.cache(false):

  1. Walk the tree; diff against the photos table on (path, mtime, size).
  2. Apply the EXIF orientation before measuring anything (sharp().rotate()), then size the derivative from the rotated aspect: landscape is cover to 1280×800, portrait is inside 640×800 with no crop. Quality 82, mozjpeg, either way. libvips shrink-on-load decodes JPEGs at 1/2, 1/4 or 1/8 scale directly, so peak memory stays around 40–60MB even for a 12MP source — which is what makes a 192MB cap at concurrency 1 survivable. The resize runs in its own systemd oneshot, not in the server process: libvips works off-heap, so its peak counts against MemoryMax while being invisible to --max-old-space-size, and split out an overrun restarts a batch job at 03:00 instead of killing the wall display.
  3. Record width, height and orientation, and compute a blurhash. Measuring before the rotation is the specific bug this step exists to prevent: a phone portrait tagged orientation 6 reports landscape dimensions, so it would never be paired and would reach the panel full-bleed and on its side.
  4. Write derivatives to cache/ on the NAS. They are ~60KB each; serving them over LAN CIFS is instant, and the SD card stays untouched.
  5. Keep the 30 most recently shown in /var/lib/hearth/fallback/ so the screensaver survives the NAS being unreachable — portraits in pairs, since half a slide is not a slide.

At display time the server streams a pre-sized file with a long cache header, and the tablet preloads the next slide so transitions never stutter. Nothing is resized at request time. The overlay drifts slowly around the screen, a few pixels per minute — static bright text held in one position for months causes image retention on an LCD.

A slide is not always one photo. The panel is 1280×800 landscape and the library is mixed, so a slide is either one landscape photo full bleed, or two portraits side by side, each taking half the width:

   ┌──────────────────────────┐   ┌────────────┬─────────────┐
   │                          │   │            │             │
   │    landscape 1280×800    │   │  portrait  │  portrait   │
   │                          │   │   640×800  │   640×800   │
   └──────────────────────────┘   └────────────┴─────────────┘

A portrait alone on this panel is either letterboxed with two thirds of the screen empty or cropped into a strip. Pairing avoids both, and two portraits from the same afternoon read as a spread rather than an accident.

  • The server composes slides, the same way it owns the theme. SSE carries one photo or a pair; the client only cross-fades what it is handed.
  • Pairs prefer photos taken on the same day, falling back to the next portrait in the shuffled queue.
  • An odd portrait is held over rather than shown alone — first candidate of the next cycle, and the queue reshuffles, so nothing is starved.
  • Each half letterboxes against its own blurred backdrop, expanded from the blurhash already on the row. Phone portraits are narrower than 4:5, so some gutter is unavoidable; nothing extra has to be generated to fill it.
  • shown_count and last_shown update for both halves, so a paired photo is not quietly favoured over a landscape one.

7.1The grocery write queue

Because groceries are writable and AnyList is the least reliable dependency, writes never go straight through:

  1. The mutation lands in a local pending_writes table and applies optimistically.
  2. A worker drains the queue against the AnyList adapter with exponential backoff.
  3. The UI shows a small pending mark on unsynced items; nothing is lost, only delayed.
  4. On the next lists-update event, server state reconciles and the mark clears.

This is what makes an AnyList outage survivable rather than infuriating.

9.1Kiosk setup, at no cost

Fully Kiosk Browser, free version, with Kiosk Mode left off. The watermark people complain about appears only when Kiosk Mode — the lockdown feature — is enabled. With it off, the free version still provides launch on boot, relaunch on crash, motion detection to wake the display as someone walks into the kitchen, screen on/off schedules, and fullscreen with no browser chrome.

What is given up is hardware-button blocking and app whitelisting, which matter for a public kiosk and not for a family kitchen. Because no PWA install is needed, the app never needs a secure context — which is why plain LAN HTTP is fine.

Beyond that: a small JS bundle, and no animation beyond opacity fades.

9.2Display schedule

Screen off at 22:00, on at 07:00, enforced by Fully Kiosk's own schedule.

  • Motion wake is suppressed during the off window. Otherwise someone getting a glass of water at 02:00 lights up the kitchen. If a night clock is wanted later, that is a different feature and a deliberate one.
  • Fully Kiosk is authoritative for the backlight. Its remote-admin API is a Plus feature, so the app cannot drive the screen on the free tier. The same window is stored in settings as quiet_hours purely so the app can pause photo rotation and stop pushing SSE updates to a dark screen. The two are kept in sync by hand; it is two fields.

The maintenance jobs already fall inside this window, which is convenient rather than coincidental — the photo resize runs at 03:00 and the nightly page reload at 04:00, both while nobody is looking. On a 2GB tablet that reload is load-bearing rather than hygiene, and running it behind a dark screen means nobody ever sees the flash.
